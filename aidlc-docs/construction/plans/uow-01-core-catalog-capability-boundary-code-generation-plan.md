The generated implementation must preserve all of the following:

1. Core remains the final authority for authenticated identity, every populated
   user/organization/project/city/inventory scope dimension, catalog state,
   capability mapping, source readiness, result shaping, and safe errors.
2. Discovery returns only safe metadata for active, authorized, mapped, and
   readiness-positive entries. Unauthorized, unavailable, unreadable, missing,
   deleted, withdrawn, or superseded entries are omitted without reason,
   counts, placeholders, or metadata disclosure.
3. Discovery performs only a bounded, non-content readiness probe. It must not
   load Climate Advisor tools, initialize executable source capabilities, invoke
   full capability operations, fetch source content, or perform full reads for
   all candidates.
4. A selected read revalidates the current request/user/scope/catalog state,
   exact capability mapping, and source readiness, then loads and executes only
   the one selected bounded capability. It never trusts discovery as a grant.
5. Stale, forged, malformed, unknown, mismatched, unauthorized, unavailable,
   missing, deleted, withdrawn, or superseded selections use the stable HTTP 404
   `capability_unavailable` contract with message
   `Requested capability is unavailable.`. The exact error envelope is owned by
   Core and must not disclose source state, IDs, labels, scope, or content.
6. Source systems retain ownership. Core calls approved module-owned bounded
   builders/services. Climate Advisor receives no S3 credentials, bearer/service
   tokens, signed URLs, raw storage paths as access mechanisms, direct database
   data, raw storage objects, or unrestricted source payloads.
7. No migration, new service, queue, cache, circuit breaker, worker pool,
   topology, shared runtime package, public API, UI, or unrelated refactoring is
   part of UOW-01.
8. UOW-02 Climate Advisor code and UOW-03 cross-service verification are not
   generated by this plan. They consume the Core contract only after UOW-01
   review and approval.

## Brown-field implementation decisions

These decisions make the approved design implementation-ready while reusing
the current repository patterns:

| Concern | Existing pattern reused | Planned Core location |
|---|---|---|
| Internal CA auth and feature gating | `requireClimateAdvisorIntegrationEnabled`, `requireClimateAdvisorServiceRequest`, `apiHandler` | New catalog capability routes |
| User/session binding | `apiHandler` service-token session plus `requireRequestUser` | New routes/service |
| Resource authorization | `PermissionService.canAccessInventory`, `canAccessCity`, `canAccessProject`, and `canAccessOrganization` with `includeResource: false` where appropriate | New catalog capability service |
| Catalog persistence | Existing `NativeInputCatalog` model and `NativeInputCatalogService` | New read-only query helpers in existing service or the new capability service |
| Capability metadata | GHGI inventory and HIAP registry definitions | New aggregate catalog capability registry |
| Bounded source execution | `buildInventoryStatusOverview`, `buildInventoryEmissionsContext`, and `buildHiapInventoryContext` | New module adapter dispatch |
| HTTP response/error lifecycle | Existing `NextResponse`, `http-errors`, `apiHandler` error handler | New routes and safe error helper |
| Test lifecycle | Existing Jest ESM setup, `setupTests`, `mockRequest`, and route/service suites | New focused Core test files plus existing auth suite if required |

The initial registry is closed and conservative. It may advertise only catalog
identity tuples that have an existing bounded Core/module implementation and a
safe readiness check. GHGI inventory-backed entries use the existing inventory
capability definitions/builders. HIAP entries use the existing persisted HIAP
inventory context boundary only when the catalog entry can be resolved to the
authorized inventory context without a content read. File/OCR/CNB/HIAP-MEED
entries without an approved bounded Core capability are omitted; this plan does
not invent a raw Markdown/storage fallback or a new module contract.

## Contract shape to implement

The Core-owned transport contract is intentionally narrow:

### Discovery request

- Authenticated user comes from the user-scoped bearer session; a body user ID
  must match it if present.
- Bounded optional request context: organization, project, city, and inventory.
- Bounded optional filters for safe capability/kind/module selection.
- No source ID, route, storage path, credential, or arbitrary capability name is
  accepted as an execution instruction.

### Discovery response

- Stable success envelope under the existing internal CA convention.
- Each entry contains only the immutable catalog ID needed for selection, safe
  kind/module/source-type labels, Core-issued capability IDs, and explicitly
  allowlisted non-sensitive labels/readiness indicators.
- No raw `sourceId`, scope IDs, storage details, catalog labels as arbitrary
  metadata, source content, omission reasons, hidden-source counts, or access
  grants.
- Readiness is represented only as an eligibility result; it does not imply
  authorization for later execution.

### Selected-read request/response

- Request contains catalog ID, Core-issued capability ID, active bounded request
  context, and the selected capability's typed input.
- Core resolves the catalog row afresh, compares the exact tuple and capability
  ID to the closed registry, checks every applicable scope dimension and current
  source readiness, then invokes one adapter.
- Success contains the existing capability-specific safe action/data envelope
  after field and size shaping.
- Selection-resolution failure is HTTP 404 with code
  `capability_unavailable` and message `Requested capability is unavailable.`.
  The response contains no catalog/source identity, state, labels, scope, or
  upstream error text.
- Authentication, malformed transport, and generic request-validation errors
  retain existing `apiHandler` semantics and do not include source metadata.

## Atomic commit and review protocol

- Each unit is test-first and independently reviewable.
- Before every commit, stage only the exact files named for that unit; never
  stage `AGENTS.md`, `.aidlc-rule-details/`, unrelated package-lock changes, or
  unrelated worktree changes.
- Commit messages must identify CC-737 and the unit outcome as listed above.
- A unit is not complete until its focused tests and proportional validation
  pass, its security assertions are reviewed, and its atomic commit exists.
- If implementation reveals an unavoidable contract or infrastructure change,
  stop the unit, document the decision in a dedicated AI-DLC question/artifact,
  and request approval before changing scope.
