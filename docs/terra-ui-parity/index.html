Scope. This covers the CityCatalyst brand theme only. The five other data-theme palettes are per-organization white-labelling — a product feature, not a design-system concern — and are deliberately out of scope here. Code values shown are the ones that render under the default theme.

And a limit worth stating: this compares names and structure, not values. The Figma REST search exposes style names and descriptions but not resolved hex or font specs, so match means the token exists on both sides under corresponding names — not that the hex agrees. Figma color tokens → code

The strongest result in the whole audit: all 25 color variables in Terra UI's Colors collection exist in the theme under corresponding names. The vocabulary is genuinely shared — alignment here is bookkeeping, not a rewrite.

content.tertiary is the most-used color token in the product — 377 references. The raw block says #7A7B9A; what actually paints is #4B4C63. Anyone reading the token file to answer "what colour is tertiary text?" gets the wrong answer — and the raw line is annotated // validated.

#7A7B9A is meanwhile hardcoded 5 times across 3 component files (PublicDashboard, CityDashboard, auth/check-email), twice more in email templates where a literal hex is legitimate, and roughly 80 times inside icons.tsx as SVG stroke/fill. So the icon set is painted with a colour the theme no longer resolves to, and no icon follows content.tertiary if it ever moves. It is also still live as interactive.control (108 uses) — both values ship, under different names.

Separately, content.tertiary-light is defined as #4B4C63 — identical to what content.tertiary already resolves to. It is a duplicate of the thing it was meant to be lighter than.

Breakpoints

Terra UI defines six responsive grids. The theme defines none.

Figma grid styleCode breakpointStatusNote
This one was implemented and then switched off. app-theme.ts lines 694–702 contain a five-step breakpoint scale — sm 600, md 905, lg 1240, xl 1440 — sitting inside a block comment. Those boundaries match Terra UI's grid definitions exactly. Somebody did the handoff correctly, and the result was commented out rather than deleted, so no history explains why. Chakra's defaults apply instead, and Terra UI's 1600+ tier was never implemented at all.

Component vocabulary

Sampled from the guidelines page (253 component nodes). This is a structural read of variant APIs, not a visual diff — that needs the in-app playground.

ComponentFigma variant APICode realityStatus
A large share of the library is Chakra v2, against a Chakra v3 implementation. Switch and Checkbox carry colorScheme=blue|cyan|green|pink|purple|teal — a prop that does not exist in v3, where the theme uses colorPalette: "brand". Alert uses variant=left-accent|solid|subtle|top-accent; the code has no Alert at all. Table uses variant=Simple|Striped|Unstyled against an in-house data-table. These read as inherited from a Chakra v2 Figma kit rather than authored for Terra, and they cannot be handed off as specified.
Design specifies disabled everywhere. Code implements it nowhere. Figma models State=Disabled across tabs, inputs, checkboxes and switches. Across every recipe in the theme there are 10 _hover, 6 _active, 5 _loading and zero _disabled. The button wrapper sets the attribute but no variant says what disabled looks like.
Nine of fifteen recipes are inert. Independent of Figma: tag, card, tooltip, accordion, progress and switch are Chakra slot recipes registered under the single-part recipes key; tab and form use keys Chakra doesn't have; text isn't a v3 recipe. They have never taken effect. Left in place deliberately — activating them would change six components at once. Any Figma spec for those components currently has no implementation to disagree with.
