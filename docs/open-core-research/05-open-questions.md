# Open questions

For the people who have to answer them. Each question names the note that holds the background.

## For Pablo (technology and architecture)

1. **The no-rebuild rule.** The benchmark ([08](04-research-directions/08-component-benchmark.md)) proposes retiring the in-house OAuth server, webhook delivery, client-side entitlements, catalogue metadata and job orchestration in favour of Keycloak or Ory, Svix or Standard Webhooks, OpenFGA plus Cedar, CKAN or DCAT-AP, and Temporal. Which of these do you accept, which do you reject, and why? This is a culture change for the team and should be pressure-tested, not assumed.
2. **Package boundary.** What is the smallest set of packages that can be carved out of the Next.js application in Q4 2026 without breaking the GCoM build, and does the strangler sequence in the roadmap ([03](03-extraction-roadmap.md)) match how the code is actually coupled?
3. **Identity server.** The 28 September session kept OAuth as "not written in stone". Given the conformance requirement and the federation path ([01](04-research-directions/01-government-identity.md)), is it cheaper to harden the in-house server or to put Keycloak or Ory behind the existing login screens? What would migrating password hashes cost?
4. **Spatial.** The area calculation uses two projections and one of them is only valid for the contiguous United States ([07](04-research-directions/07-spatial-first.md)). Is the live geometry column PostGIS-typed or text, as the migration says? Does the place entity plus edge table plus crosswalk design fit the warehouse, and should it live in the application database or the warehouse?
5. **Multi-replica weaknesses.** OAuth code replay protection and the rate limiters are in memory while the deployment runs two replicas ([01-component-inventory.md](01-component-inventory.md)). Confirmed, and tolerated for now?
6. **Service-to-service authentication.** The prioritisation services appear to accept calls with no authentication, relying on cluster networking. Are network policies in place?

## For Milan (full stack)

1. **Record envelope.** Can the version history keyed by inventory become a generic envelope (identifier, version, supersedes, entity, issuer, schema, hash, signature) without a rewrite of the GHGI tables, and what is the migration path for existing versions? ([05](04-research-directions/05-verifiable-records.md))
2. **Entitlement enforcement.** Module access is checked in three API files and otherwise in the UI. What would server-side enforcement through one authorisation call cost, and which routes would break?
3. **SDK pipeline.** The workflow's trigger path does not exist. What does publishing the TypeScript and Python SDKs to a registry on every tagged release need?
4. **Export bundle.** A complete tenant export (records, documents, consent and policy records, access log) that another instance can import: which parts exist in the GDPR export already, and what is missing?
5. **Tests.** No tests cover the MCP server or personal access tokens, and the global-api test step may not fail the build. What is the minimum test estate for the core packages before they are published?

## For Mirco (AI)

1. **Agent identity and scopes.** Separate client identities per agent with tenant-scoped scopes, audience binding and no token passthrough are required by the current MCP revision ([04](04-research-directions/04-ai-agent-governance.md)). What does this mean for the Climate Advisor's service token and the capability registries, which today are three parallel definitions?
2. **Audit log and provenance.** The proposed hash-chained tool-call log and the provenance fields on records (generated by run, attributed to agent, on behalf of user, derived from, human reviewed by). Where do these hook into the agent service's run model?
3. **Gateway.** Would an Apache-licensed MCP gateway in front of the six tools replace work you would otherwise do, or add a hop you do not want?
4. **No training on city data.** Which providers and retention modes does each instance use today, and can the Bedrock retention mode be enforced organisation-wide for the AWS deployments?
5. **Prompt injection through scanned documents.** Public-sector PDFs are long, multilingual and often scanned, and no benchmark covers injection through OCR noise. Is a small benchmark on real municipal documents worth a quarter?
6. **Cryptographic experiments.** Of the three one-quarter experiments in [09](04-research-directions/09-cryptographic-control.md) (signed envelope pilot, agent run log with external anchor, capability delegation chain), which would you run first?

## For C40 and GCoM

1. **Badge and verification wording.** GCoM and CDP "validate" completeness; "verification" in climate accounting means third-party assurance. Should a badge credential issued by the service state its scope of check explicitly, and what process governs disputes and revocations? ([05](04-research-directions/05-verifiable-records.md))
2. **Who may sign for a city.** Which role may publish a record and request a badge, how is that authority evidenced, and what happens after an election?
3. **Federation anchor.** If partner tools are to accept the same city login, someone must run the trust anchor. Would GCoM or C40 run it, under what governance, and would CDP-ICLEI Track and an ICLEI tool join?
4. **Data roles.** Which legal entity is controller for personal data in city uploads, and for the inventory itself: C40, GCoM's host organisation, or the city?
5. **Residency.** Which countries require separate instances by July 2027, and who pays for them?
6. **Partner identity setups.** May the service document how CDP-ICLEI Track handles city accounts, as published in its user guide, in a shareable architecture note?

## For OEF leadership

1. **Fork versus branch.** The London sessions deferred this to after the MVP. The benchmark's condition for the evolve strategy is a published package boundary within six months; without it, a partner's branch and the trunk drift and the second network inherits two codebases. Is the boundary a Q4 2026 commitment?
2. **Governance home.** Evolving the codebase keeps OEF as steward. If the core is to serve health or biodiversity networks, does it need a neutral foundation home, and when?
3. **Deliberation.** The build-or-integrate choice is the one worth putting to a structured deliberation, with the benchmark table as input and the question narrowed to "evolve under the no-rebuild rule versus a fresh thin core".
